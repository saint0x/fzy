4. The compiler currently has a real `core.log` build-path regression: `fz check` accepts programs importing `use core.log;`, but `fz build` fails before compiling user code with `failed parsing embedded core stdlib module 'log': unexpected token in expression`. This reproduces both in the main `fzyagent` workspace and in a minimal standalone program:
```fzy
use core.log;

fn main() -> i32 {
    log.info("hello", "");
    return 0
}
```
`fz check` passes on that repro, while `fz build --backend cranelift` fails; removing the `core.log` import makes `fz build` succeed again. This needs to be fixed in the compiler/runtime stdlib embedding path rather than worked around in downstream apps, because it blocks normal build/run validation for any project that uses the standard logging surface.

5. HIR lowering repeatedly scans the module, rebuilds environment maps, and clones function bodies into typed structures, making it one of the highest-latency compiler phases before native codegen. `hir::lower` builds `struct_defs`, `enum_defs`, `trait_defs`, `trait_impls`, and `type_aliases` through separate whole-module scans in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:337), then clones function bodies into `TypedFunction` values in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:581). This should be split into staged declaration indexing and body inference passes with shared immutable metadata so large-module compile time scales better.

6. HIR hot paths repeatedly allocate empty maps and use string-keyed lookups where immutable shared defaults or interned ids would be materially cheaper. Item checking paths construct fresh `HashMap::new()` placeholders for globals and mutability state in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:437) and [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:498), and the file broadly relies on `HashMap<String, ...>` for high-volume compiler metadata. This should be tightened by reusing singleton empty maps and gradually moving hot symbol/type lookups to interned ids rather than repeated owned strings.

12. `driver::command.rs` and `driver::pipeline.rs` are both monolithic enough that they likely hurt not just runtime behavior but also incremental Rust compile times and maintainability of future perf work. The files are currently about 19.6k and 15k lines respectively, and they mix orchestration, policy, I/O, formatting, diagnostics, and command-family specifics into extremely large compilation units. They should be split by command family and phase responsibility so that profiling, caching, and optimization changes can be targeted without dragging unrelated code through rebuilds.

18. The stdlib HTTP surface is too large and mixed-responsibility to optimize effectively as-is, and it likely hides avoidable string, map, and parsing allocations across transport and protocol concerns. [crates/stdlib/src/http.rs](/Users/deepsaint/Desktop/fozzylang/crates/stdlib/src/http.rs:1) combines socket lifecycle, request parsing, header handling, payload logic, and deterministic backend behavior into one 2.5k-line module. It should be split into parser, transport, header, and payload layers so borrowed parsing and focused benchmarking can be applied where they matter most.


24. Several HIR analysis passes clone large branch-local binding maps at every `if`/`else` and loop split, which creates avoidable superlinear CPU and allocator pressure on control-flow-heavy modules. GPU contract analysis clones binding environments in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:2250), and live-borrow analysis repeats the same pattern in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:3812). These analyses should switch to delta-based branch state, persistent maps, or reversible mutation stacks so control-flow validation does not keep copying whole `BTreeMap` environments.

28. Cold parse misses rebuild a giant concatenated source blob and merge every module AST into one owned aggregate, which adds avoidable string growth, allocator churn, and tree movement before HIR even begins. `parse_program_uncached_with_root_source` in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:7117) parallel-loads module ASTs, appends every module into `combined_source`, removes each loaded module from the map, and merges all imported ASTs into the root. This should move toward a graph-backed parsed representation with lazily materialized combined text only for the specific consumers that actually need it, so cold `check`, `verify`, and deterministic planning paths stop paying full merge cost by default.

29. Native backend emission lacks content-addressed artifact reuse, so identical FIR plus identical backend/profile/link settings still rebuild objects, runtime shims, archives, and linked outputs on repeated runs. LLVM emission in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14681) rewrites `.ll` and re-invokes the external toolchain each time, while Cranelift emission in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14748) and library emission in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14273) rebuild objects and runtime shims unconditionally. The build pipeline should cache backend artifacts by FIR hash plus profile, backend, runtime-shim inputs, and linker-affecting settings so warm `build` and `run` latency drops substantially without weakening correctness.

30. Deterministic non-scenario `run` and `test` flows currently duplicate orchestration work by first synthesizing bridge artifacts from language analysis and then rerouting through scenario execution for host-backed modes. Host-backed deterministic routing in [crates/driver/src/command.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/command.rs:408) and [crates/driver/src/command.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/command.rs:805) generates a trace path, runs `run_non_scenario_test_plan_with_root_guidance`, extracts a generated scenario, and then immediately invokes `fzscenario::run_scenario` or `run_tests` on that derived scenario. These flows should share one execution model or at least one reusable intermediate package so host-backed deterministic commands do not pay both the language-side planning cost and the scenario-side execution setup cost back to back.




40. Cranelift emission still rebuilds and clones more per-function semantic state than necessary, which makes the supposedly fast dev backend pay extra setup cost on every compile. Both native artifact emission paths build fresh function-signature and descriptor maps in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14325) and [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14795), and each function passes `function.local_types.clone()` into `clif_emit_function_cfg` in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14496) and [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:14971). The Cranelift path should share immutable per-module metadata and stop cloning large local type maps per function so warm dev builds better reflect the backend’s intended low-latency role.

44. The parser still lexes each source file into a fully owned token buffer before parse-time consumption, which makes `check`, `verify`, and especially LSP-style feedback pay an eager allocation cost proportional to total file size even when only a subset of structure is needed. `parse` in [crates/parser/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/parser/src/lib.rs:113) constructs `Lexer`, materializes `tokens = lexer.lex()`, and only then begins syntactic analysis through `Parser::new(tokens, module_name)` in [crates/parser/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/parser/src/lib.rs:122), while `TokenKind` stores owned `String` payloads for identifiers and string literals in [crates/parser/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/parser/src/lib.rs:12). The frontend should move toward borrowed token slices, lighter token payloads, or an incremental parse representation so edit-check and editor latency stop paying full eager token ownership costs on every request.

45. Warm compiler cache lookups still hash the entire concatenated module source before they can hit, so cache-hit latency remains `O(total_source_bytes)` even when parsed and lowered state is otherwise reusable. `lower_fir_cached` computes `module_hash = sha256_hex(parsed.combined_source.as_bytes())` in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:700), and that `combined_source` itself is rebuilt as a giant merged string during cold parses in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:7131). This should switch to a cheaper incremental fingerprint derived from per-module stamps or cached content hashes so warm `check`, `verify`, and `build` runs do not spend noticeable time rehahsing the full logical program just to discover a cache hit.


52. Parsed-program cache hits still serialize callers behind a global mutex and restat every module file before returning, so warm-path latency keeps a built-in lock-and-filesystem tax even before the cloned `ParsedProgram` is handed back. `cached_parsed_program` in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:7194) takes the global `PARSED_PROGRAM_CACHE` lock, walks every stored stamp, and calls `module_stamp` on each path before declaring a hit. This should move to read-optimized cache concurrency plus cheaper invalidation state so warm `check`, `verify`, `build`, and editor-oriented requests do not bottleneck on one mutex and a full per-module metadata pass.

54. Scenario checkpointing currently clones the entire execution world for rollback, which makes nested-step validation, failure-expected branches, and any future exhaustive reduction work pay worst-case copy costs in proportion to all tracked runtime state. `checkpoint` in [crates/fzscenario/src/runtime/engine.rs](/Users/deepsaint/Desktop/fozzylang/crates/fzscenario/src/runtime/engine.rs:2917) clones RNG state, virtual clock state, KV and FS stores, host filesystem snapshots, proc and HTTP rules, network queues and inboxes, partition state, and memory tracking before `restore` writes it all back in [crates/fzscenario/src/runtime/engine.rs](/Users/deepsaint/Desktop/fozzylang/crates/fzscenario/src/runtime/engine.rs:2940). This should move toward delta-based rollback, persistent data structures, or reversible mutation logs so exhaustive and adversarial scenario tooling can scale without clone-the-world latency spikes.







68. The compiler's internal phase boundaries are still blurrier than they need to be, which creates duplicated semantic carriers and repeated lowering work across `HIR`, `FIR`, verifier, and native backend preparation. `TypedModule` and `TypedFunction` in [crates/hir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/hir/src/lib.rs:7) remain the semantic source for many downstream checks, `FirModule` still carries full `typed_functions` alongside lowered CFG data in [crates/fir/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/fir/src/lib.rs:82), the verifier still consumes those high-level functions directly in [crates/verifier/src/lib.rs](/Users/deepsaint/Desktop/fozzylang/crates/verifier/src/lib.rs:159), and native codegen builds another canonical control-flow/data plan in [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:10310) and [crates/driver/src/pipeline.rs](/Users/deepsaint/Desktop/fozzylang/crates/driver/src/pipeline.rs:11213). The optimization direction here should be to sharpen the existing contracts rather than add a premature general MLIR tier: keep `HIR` as the semantic truth, make `FIR` or its immediate successor the single downstream analysis contract, promote the native canonical plan into a clearer first-class lowering stage, and reserve any MLIR-style integration for a future dedicated GPU `Kernel IR` path instead of adding another broad middle layer to the whole compiler.
